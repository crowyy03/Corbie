# Decisions

Running log of implementation decisions not covered by the spec. Newest at the bottom.

## 2026-09-05

- Xcode project is generated from `project.yml` via XcodeGen so that project structure lives in a reviewable text file. Regenerate with `xcodegen generate` after editing `project.yml`.
- `CorbieCore` declares `.macOS(.v14)` alongside `.iOS(.v17)` so that the package builds and tests with `swift build` / `swift test` on a Mac without Xcode. UIKit-only code is guarded with `#if canImport(UIKit)`.
- The spec's `Task` entity is named `TaskItem`, `List` is `ChecklistList`, to avoid clashing with Swift standard library types.
- Tests use Swift Testing. Command Line Tools include neither XCTest nor Testing, so `scripts/test_core.sh` adds `swift-testing` 6.1.3 as an opt-in dependency through `CORBIE_EXTERNAL_TESTING=1` (6.2+ needs `_TestingInterop`, which the CLT toolchain lacks). Xcode ignores the flag and uses its bundled Testing.
- Core Data model is built programmatically (`NSManagedObjectModel` in code) instead of `.xcdatamodeld`, because `momc` is not available outside Xcode and a code model is diffable and unit-testable against the CloudKit rules (optional/default attributes, no unique constraints, no ordered relationships, inverses everywhere).
- Module 00: the Xcode project is generated into the repository root and committed, so the founder can open it without XcodeGen installed. `project.yml` stays the source of truth; `Configs/` holds the per-target entitlements and the Info.plist files XcodeGen writes.
- Module 00: XcodeGen 2.46 cannot put a Swift package test target into a scheme ("Spec validation error: Scheme "Corbie" has invalid test target "CorbieCoreTests""). The Corbie scheme therefore tests `CorbieTests` and `CorbieUITests`; `CorbieCoreTests` runs through `scripts/test_core.sh`.
- Module 00: one string catalog, `Corbie/Resources/Localizable.xcstrings`, is compiled into the app, the widget and the share extension, so a key resolves the same way in all three bundles.
- Module 00: the tab skeleton uses stock SwiftUI styling. It moves to `CorbieCore/Design` tokens and components once Module 01 lands.
- Module 00: `NSUserNotificationsUsageDescription` is in the app Info.plist because the module prompt asks for it; iOS does not read that key, the notification permission prompt has no usage string.

## 2026-09-05 (review pass)

- Every child object is assigned to the persistent store of its parent (`context.assign(_:toStoreOf:)`) and a new `Space` is assigned to the private store explicitly. Core Data on the current toolchain already places a related insert in its parent's store and an unrelated one in the first store, so this is not a behaviour change; it makes the placement intentional instead of implicit, and `StoreAffinityTests` pins it with a real two-store on-disk stack.
- `CoreDataStack.store(for:)` falls back to "the only store" only when that store is in memory. On disk, a scope whose file is not loaded returns nil, so accepting a share can no longer land in the private store when the shared one failed to open.
- `CoreDataStack(storesIn:)` opens the private and shared stores in a given directory without CloudKit. It is how the two-store tests run on macOS.
- Leaving and deleting a space are now separate paths guarded by the store the `Space` lives in. A participant leaves by deleting the `CKShare` from the shared database and purging the mirrored zone (`purgeObjectsAndRecordsInZone`), never by deleting the mirrored objects, which would export deletions of the owner's records. The owner deletes the share from the private database and then the local objects. A missing share is an error, not a silent local wipe.
- `PersistentHistoryObserver` merges `NSPersistentStoreRemoteChange` transactions written by the other processes into the view context, keeps its token in the App Group defaults under `history.token.<author>`, purges history older than seven days and posts `WidgetReloadRequest` after a merge.
- `Member` stores `appleUserHash`, the SHA-256 of the Sign in with Apple identifier, per spec section 7. The raw identifier stays in the Keychain and never reaches Core Data or the partner's device. The repository still takes the raw id and hashes it at the boundary.
- `Vote` answers are one `VoteResponse` record per member instead of one JSON blob, so each device writes only its own row and the property merge policy cannot drop a partner's answer. `VoteDTO.responses` is unchanged.
- Plan money has one base: `savedAmount` is the "Saved so far" figure the user types (spec 6.6), `progress` and `leftAmount` are both measured against it, and expenses are reported separately as `spentAmount` and `overspentAmount`. Expenses do not move `savedAmount`.
- `revealedAt` is stamped only when everyone has answered or when someone reveals the vote by hand. `canSeeResults(as:)` additionally requires the viewer to have answered, so "Reveal only when both answered" turned off never shows one partner the other's choice for free (spec 6.9).
- The pinned Shopping list takes its title from the caller. Package code cannot resolve the app's string catalog, so a `String(localized:)` key persisted from `CorbieCore` would be stored and synced verbatim.
- An author-only list denies a tick when the member or the author is unknown, falling back to the list creator when the item records no author.
- The app is iPhone only: `TARGETED_DEVICE_FAMILY = 1` on the app, widget and share targets. The design is portrait-only and single column, and the Info.plist already declares portrait alone.
- `CKSharingSupported` is in the app Info.plist and `AppDelegate.application(_:userDidAcceptCloudKitShareWith:)` calls `CloudKitSharing.acceptShare(metadata:)`, so an invitation link actually joins the space.
- Each tab is a bare `NavigationStack` around its feature root; the feature view owns its title and toolbar and adds the pill with `.toolbar { UsPillToolbarItem() }`. The pill is the `CorbieCore` `UsPill` component, which already meets the 44pt tap target.

## 2026-09-05 (module 04, tasks)

- The Tasks list shows open tasks only. Marking one done takes it off the screen; there is no "Done" section in v1, the weekly count is a v2 line in the spec.
- `TasksViewModel` loads DTOs from `TaskRepository` and reloads on `WidgetReloadRequest` and on `scenePhase == .active` instead of wrapping an `NSFetchedResultsController`. Every repository write already posts that notification, so the list follows local edits, the widget intents and the share extension through one path, and the same view model runs in tests against an in-memory store.
- Chip counts come from `repositories.tasks.counts`; the sections filter the loaded list in memory. Counts and grouping therefore agree without a second round trip per chip.
- Read-only mode gates changes, not only creation: take, hand back, done and delete run through `premiumGate.require(.edit)`, "+" and the editor through `.create` / `.edit`. Spec 6.12 puts "создать/изменить" behind the paywall, and the calendar stays untouched.
- Delete is offered to the author, and to anyone when the task carries no author id (tasks created before `createdByMemberId` was written, or seeded ones).
- The "Who" control drops the Partner segment until somebody joins the space, because there is no member id to assign to.
- Due-today notifications are scheduled by every device that sees the task, not only by the assignee's. `NotificationScheduler.scheduleTaskDueToday` cancels before it schedules, so saving an edit re-points the reminder and clearing the date removes it.
- Notification authorization is requested the first time a task with a due date is saved, not at launch (architecture 18.12).
- `AnalyticsEvent.taskHandedBack` ("task_handed_back") is emitted by the client, but it is not in `AnalyticsEvent.allowedNames`, in `docs/03_TECH_ARCHITECTURE.md` section 13, or in `server/supabase/functions/_shared/events.ts`. The server drops unknown names per event, so the batch still lands; the event starts counting once those three lists get it.
## 2026-09-05 (module 05, calendar)
- The calendar range fetch floors its start to `Calendar.startOfDay`. `CoreDataEventRepository.events(spaceId:from:to:)` matches `endAt >= from OR (endAt == nil AND startAt >= from)`, so an event earlier today with no end would drop out of a range that starts at "now".
- All-day events written by the editor store `endAt` at 23:59:59 of the last day. EventKit hands imported all-day events an exclusive midnight end, so `CalendarEntry.inclusiveEndDay` reads an end that lands exactly on midnight as exclusive and keeps our own 23:59:59 ends inclusive. Both conventions then draw the same number of days.
- Auto dates are merged into the grid and Upcoming, never stored. A stored event hides the virtual one when it falls on the same day and means the same thing: a birthday for the same person, a birthday without a person for a member birthday, an anniversary for either the together-since or the wedding date.
- Auto dates are generated twice, anchored on today and on the first day of the visible month, so a future month shows that year's occurrence. The calendar entry id carries the day, so two occurrences of the same auto date can coexist.
- Multi-day events are ice bars with lanes; a week row grows with its lane count instead of hiding a bar behind a "+N" marker. Single-day entries are dots under the day number, at most two.
- The calendar reloads on `WidgetReloadRequest`, debounced by 250 ms. That covers edits made on the pushed detail screen, a bulk import and events merged from the partner by `PersistentHistoryObserver`.
- "Add to iPhone Calendar" asks for write-only access (`EKEventStore.requestWriteOnlyAccessToEvents`), which needs `NSCalendarsWriteOnlyAccessUsageDescription` in the app Info.plist. `project.yml` does not declare that key yet, so the button reports "no access" instead of asking: requesting without the key terminates the app.
## 2026-09-05 (module 06, wishes and share extension)
- The wishes list is a plain `List` with card rows instead of a `ScrollView` of cards: "Mark as gifted" and "Delete" are swipe actions, and iOS 17 has no swipe API outside a list. Rows keep the card look through `listRowBackground(.clear)` and hidden separators.
- Deleting a wish sits next to "Mark as gifted". The spec names only gifting, but a wrong link has to be removable and gifting would park it in "Fulfilled" forever. Both partners can delete, like every other object in the space.
- The "≈" figure renders from the FX table already cached in the App Group (`FXService.cachedRates`), one table per source currency, and only then refreshes in the background. The list never waits for the network and never shows a spinner for a price.
- `needsParse` is stored for every wish saved with a link that has not parsed yet: the offline share, a parse timeout, or manual entry with a link. `WishesView` retries at most five of them per appearance while the network path is satisfied and never retries the same wish twice in one session.
- The share extension cannot show a paywall, so it reads the entitlement the app cached (`EntitlementService.cachedState`: keychain entitlement plus `Space.trialEndsAt`) and, when the trial is over, shows one line asking to open Corbie instead of a save button.
- `AnalyticsEvent.wishFulfilled` ("wish_fulfilled") was added to CorbieCore because the module prompt names the event. The server allowlist (`server/supabase/functions/_shared/events.ts`) and its test still reject the name and need the same addition.
- Source tags on cards are brand names (Amazon, Etsy, TikTok) and stay untranslated. `store` falls back to the link host, `manual` shows nothing.
## 2026-09-05 (module 07)
- Big lists active and completed plans; archiving takes a plan out of the tab. There is no archive screen in v1, so archive is the way to put a finished plan away, and `corbie://plans/<id>` still opens it.
- Plan money is shown in the plan currency, not in the space display currency. `targetAmount` and `savedAmount` are stored in the plan currency, so showing them in another currency would mean converting numbers the user typed at a rate that changes under them. A new plan defaults to the space currency, which is what makes the two agree in practice; only an expense in another currency is converted, once, at add time, with the rate kept on the expense.
- The pinned Shopping list is created the first time the Plans tab loads and is not premium gated: it is the container the Shopping widget and its App Intent expect, not user content. It cannot be deleted from the list menu, only edited.
- Ticking an item, reordering, clearing done and adding an expense all go through `PremiumGate`, as create or edit. Reading stays open, so a read only pair still sees every plan, list, item and place.
- List and Map is one screen with two modes behind a toolbar button, not a second navigation destination. Reordering uses the system `EditButton` because a plain SwiftUI `List` only starts a drag in edit mode.
- `AnalyticsEvent` gained `listItemChecked` and `listMapOpened` (`list_item_checked`, `list_map_opened`). They are deliberately absent from `AnalyticsEvent.allowedNames`, the server allowlist and architecture section 13; the server drops unknown names one by one, so the events are recorded and discarded until all four places are updated together.
- Deleting a plan or a list is not in the module prompt but is the only way out of a mistyped one, so both sit behind a confirmation in the screen menu.
## 2026-09-05 (module 08)
- `Capsule.openedByMemberIdsData` is gone. Every open is now a `CapsuleOpen` row (id, memberId, openedAt) under a cascade relationship with a nullify inverse, the same shape as `VoteResponse`, so two partners who open offline no longer overwrite each other. `Capsule.openedAt` is derived from the earliest child instead of being stored, which removes the second copy of the same fact. `CapsuleDTO.openedByMemberIds`, `openedAt` and `isReadByBoth` are unchanged; duplicate rows for one member are collapsed when the DTO is built, so one device opening twice cannot fake "read by both".
- The Us tab shows the hub inline and carries no Us pill: the pill exists to open the hub, and that tab already is the hub. Its "+" offers a new capsule or a new vote, the only two things the hub creates.
- `UsHubView` closes the Us sheet when the premium gate raises a paywall request. `RootView` presents the hub and the paywall as two sheets on the same `TabView`, and SwiftUI presents only one of them at a time.
- The counters card takes the second number from `ImportantDates.nextImportantDate`. "Custom pinned event" is read as a calendar entry of kind `anniversary`, because `Event` has no pinned flag.
- Capsules and votes are gated with `PremiumAction.capsules` and `.votes` instead of `.create`, so the paywall can name the reason. Opening a capsule and answering a vote stay ungated: both are reading, not creating.
- A capsule's open-day notification is scheduled by the author when saving and by anyone who opens the capsule list, because only the author's device runs the editor. A launch-time reschedule of everything belongs to the notifications module.
- `AnalyticsEvent.voteAnswered` was added because module 08 names `vote_answered`. `AnalyticsEvent.allowedNames`, `NetAnalyticsTests` and the server allowlist still do not carry it; syncing them is outside this module's scope.
- People opens `PeopleEntryView`, a placeholder inside `Features/Us` that only shows the count. The People module replaces it.
## Module 09 (People, gift ideas, date radar)
- People gates on opening an editor (`premiumGate.require(.create)` for a new person or gift idea, `.edit` for changing, toggling or deleting one), not on saving. Gating at save would present the paywall on top of an open sheet, and RootView presents the paywall from the root. Viewing people and their gift ideas stays free.
- A radar refresh cancels every pending `dateRadar` notification and reschedules from the current input, so a deleted person, a cleared birthday or a picked gift cannot leave a stale reminder behind. It runs when the People list or a person opens, after every edit and after a delete.
- Radar scheduling failures are logged, not shown as a toast: scheduling is housekeeping, and a denied notification permission would otherwise toast on every visit to the screen. Repository failures the user asked for (save, delete, toggle) still toast through `environment.report(_:)`.
- `PeopleRadarSummary` (Features/People) turns a `RadarLine` into the mono sub-line "14 days to go / 3 ideas saved". It holds no view or environment types so the calendar can reuse it as is; the widget extension does not compile app sources, so a widget needs it moved into `CorbieCore` first. Widgets already receive `RadarStatus` through `WidgetDataProvider`.
- Birthdays are month and day only. They are formatted with `Date.FormatStyle` on a fixed leap reference year (2024) with the month and day fields alone, so the year never shows and 29 February stays a valid birthday.
- A gift idea's currency follows the space display currency, is picked from `FXService.supportedCurrencies()`, and is dropped when the price is cleared.
- The person editor hides the owner picker while the space is solo and files the person under the current member.
- Radar notifications carry the route `corbie://people/<id>`, which `CorbieRoute` understands but the app-side `Route` and `AppState` do not have a case for yet, so tapping one opens the app without landing on the person.
## 2026-09-05 (module 03, onboarding and pairing)
- `RootView` switches on `AppEnvironment.session`: `.loading` shows a bare mark on `bg`, `.signedOut` replaces the whole screen with the onboarding flow (no tab bar underneath), `.signedIn` shows the tabs with the paywall, the Us hub and the join sheet attached.
- The onboarding flow keeps its own step state and calls `reloadSession()` only when it is finished. If it created the space and member first and reloaded, the session would flip to `.signedIn` mid-flow and the tabs would replace the profile step.
- With a join code in hand (deep link) the flow does not create a local space at sign-in: it collects the profile and goes straight to the join step. Cancelling there creates the solo space. This avoids creating a space only to delete it two screens later.
- Joining replaces the space on this phone. Core Data cannot move a `Member` between the private and the shared store, so the joiner's member is deleted with the local space and created again inside the joined space, which is also what makes the second member appear on the owner's device. Joining is therefore refused when the local space is already shared or holds content (tasks, events, wishes, plans, lists, capsules, votes, people): merging two spaces needs a data hand-over that v1 does not have.
- `redeemInvite` burns the code, so `JoinViewModel` keeps the redeemed `InviteShare` and a retry resumes at the CloudKit step instead of asking the server again.
- After `acceptShare` the mirrored objects arrive asynchronously; the join step polls `spaces.space(id:)` for the redeemed space id (30 tries, 500 ms apart) before writing the member into it.
- The trial extension for the second member is guarded by a flag per space id in the App Group defaults (`corbie.trial.partnerextension.<id>`), because `extendTrial` moves `trialEndsAt` to `now + 7d` every time it runs.
- `PartnerJoinWatcher` listens to `WidgetReloadRequest` (posted by every repository write and by `PersistentHistoryObserver` after a CloudKit merge) and re-checks on `scenePhase == .active`. It only reloads the session when the trial has to be extended or when the partner is not in the session yet: every repository write posts that notification, and `reloadSession` writes `lastSeenAt`, so an unconditional reload would loop. It is started from the signed-in subtree only, so it cannot pull the onboarding flow into `.signedIn` halfway through.
- `POST /session` lives in `Corbie/Features/Pairing/SessionService.swift` on `URLSession`, not in the core `APIClient`, because the core client has no session endpoint yet. A failed exchange is a toast, not a stop: the Apple identity token in the Keychain still authenticates `/invite` for about ten minutes.
- Apple credential revocation signs out and keeps local data. The launch check only signs out on `.revoked`; `.notFound` is left alone, because a simulator without an iCloud account answers `.notFound` for a perfectly good stored identifier.
- The pill button style in `CorbieCore/Design` is internal, so the `ShareLink` on the invite screen repeats the filled pill look locally. Making `CorbiePillButtonStyle` public would remove the duplication.
- CKShare is created with `publicPermission = .readWrite` (architecture section 3.2 said `.none`): CloudKit only lets a non-participant accept a share URL when the share is open to anyone with the link, and the joiner is never pre-registered as a participant. Access is still protected by the one-shot 15 minute invite code that the server maps to the URL.
## 2026-09-06 (module 10, widgets)
- The bundle is split into two `@WidgetBundleBuilder` properties (`homeWidgets`, `lockScreenWidgets`): one block takes at most ten widgets and v1 ships thirteen.
- Home widgets turn the system content margins off and pad themselves by `CorbieSpacing.s`. The default margins leave 126pt of height in a medium widget, which does not fit three rows at the 44pt tap target; 12pt leaves 134. Lock screen widgets keep the system margins.
- Tasks, FreeTasks and Shopping carry no heading. Three 44pt rows fill a medium widget on their own, and those three are the interactive ones where the tap target rules. PartnerWishes and UpcomingDates are not interactive, so their rows are 30 and 34pt and they keep a mono caps heading.
- `WidgetDataProvider.shoppingLimit` drops from 5 to 3, so that `remaining` counts what the widget actually leaves out.
- The wishes widget shows title and price, no thumbnail: `WidgetWish.imageURL` is a remote URL and a timeline render cannot fetch it.
- Deep links name the destination even where `Router.route(for:)` (Corbie/App/Router.swift) does not resolve it yet: `corbie://paywall` from every locked placeholder, `corbie://us` from the OurDay counter, `corbie://lists/<id>` from Shopping. The router understands tasks, calendar, wishes, plans, plans/<id>, capsules, votes and join; the other three open the app without navigating until it learns them.
- `RadarText` in CorbieCore holds the radar wording for the widgets, which cannot import app sources. `PeopleRadarSummary` (Corbie/Features/People) still holds the same assembly for the app; the two should become one file once the app side can be touched.
- Lock screen views use system text styles instead of the `CorbieFont` tokens. The counter token is 56pt and an accessory family renders small and monochrome, so the app scale does not fit.
- Widgets render in the system appearance. `ThemeStore` keeps the in-app light or dark override in the App Group defaults, but `preferredColorScheme` has no effect on a widget, so an override set in the app does not reach the home screen.
- Marking a task done from a widget cancels its due-today notification. The client comes in through `TaskIntentRunner.markDone(notifications:)`, and `IntentNotifications.client()` returns nil when the process has no bundle identity: `UNUserNotificationCenter.current()` raises there, and `swift test` runs without one.
- An unconfigured PlanProgress widget shows the newest active plan, because `PlanRepository.plans` sorts by `createdAt` descending.
## 2026-09-06 (module 11, paywall and StoreKit)
- `PaywallReason.banner` is now `.trialEnding` (raw value `trial_ending`) and sits next to `.trialEnded`. The banner raises one of the two depending on whether the trial is still running, so the paywall can open with a line that matches what the couple just saw.
- The trial banner is a `safeAreaInset` on each tab root, not a row inside every feature view. It therefore stays put while the feature scrolls, never reaches a pushed screen, and no feature had to be edited to carry it.
- `TrialBanner` prints the day count in its own capsule, so the banner line is "Trial ends soon." with no number in it. A plural variation without the number in the value is rejected at build time ("Plural variation requires referencing the number in the string"), and repeating the count next to the capsule reads like a bug. The VoiceOver line (`paywall.banner.trial.spoken`) is a normal plural and does carry the number.
- The Us hub is a `fullScreenCover` now, with an `xmark` close control and no navigation title, because the hub view already carries the big "You two" header. `UsHubView` still closes itself when the gate raises a paywall; RootView holds the paywall back until the cover has actually left the screen (`isUsHubOnScreen`), so the sheet is never asked to present over a dismissing cover.
- `PaywallRuntime` is a view modifier on `RootView` rather than work inside `AppEnvironment.bootstrap`: it starts the `Transaction.updates` listener, hands `StoreService` the analytics recorder, refreshes the entitlement when the space id appears and on every `scenePhase == .active`.
- `trial_started` is recorded by the client the first time a device resolves a running trial for a space, keyed by `corbie.trial.started.<spaceId>` in the App Group defaults. The trial itself starts with the space, so there is no purchase moment to hang the event on.
- `DebugMenuView` is `#if DEBUG` and its labels are `Text(verbatim:)`, not catalog keys. It is a developer tool, and its strings would otherwise reach the translators.
## 2026-09-06 (module 12, settings, notifications, account lifecycle)
- Remote notifications are two layers. `PersistentHistoryObserver` already merged CloudKit transactions; it now also hands every change it merged to a handler as `RemoteChangeRecord` (entity name, object URI, change type, updated property names, transaction author and context name). `RemoteChangeResolver` turns those records into DTOs, `RemoteChangeClassifier` is a pure function from `[RemoteChange]` plus a viewer to alerts, and `RemoteChangeNotifier` glues the three to `NotificationScheduler`. Only the classifier holds the nine rules of spec section 9, so it is the only piece the tests need.
- A change counts as somebody else's when its transaction author is not one of our own (`app`, `widgets`, `share`, `tests`). The CloudKit import writes under `NSCloudKitMirroringDelegate.import`, so the partner's writes and this phone's own writes are told apart by the author alone, without comparing object graphs.
- Notification permission is asked on the first resolved remote change from the other device, not on the first alert. A partner marking a task done produces no alert but is a joint action, and the ask happens there. The flag lives in the App Group defaults under `corbie.notifications.jointaction`, so it survives a relaunch and the ask happens once.
- Alerts are delivered as local notifications with no trigger (`CorbieNotificationRequest.isImmediate`), which is how a silent push turns into something visible. Their identifiers carry a `corbie.remote.<kind>.` prefix so `cancelEverything` can find them next to the scheduled ones.
- The nine settings toggles map to preferences one to one (`SettingsNotificationToggle`). Turning one off cancels the pending local notifications its preference gates (`NotificationScheduler.cancelAll(kinds:)`); turning one on runs `NotificationBacklog.resync`, which reschedules open tasks with a due date and every unopened capsule. The five remote kinds have nothing pending to cancel: they fire the moment the change arrives.
- `NotificationBacklog.resync` also runs once per launch, after the session loads and only when notifications are already authorized. That closes two gaps other modules left: a capsule scheduled only on the author's device, and a due-today alert that survived its preference being switched off.
- Notification actions go through `TaskIntentRunner`, the same path the widgets use, so a task completed from a notification creates its next occurrence exactly like one completed in the app. `AppEnvironment.bootstrap` points `IntentPersistence.shared` at the app's own controller first, otherwise that runner would open a second CloudKit container inside the app process. The Done action also cancels the due-today alert, which the widget path still does not.
- The VOTE action opens the app on the vote instead of casting one. A notification action cannot show four options, and answering blind would be worse than one tap into the screen that hides the partner's answer until you have answered.
- `Route` gained `.task(UUID)`, `.people` and `.person(UUID)`, and `Router.route(for: CorbieRoute)` maps the core route strings that notifications carry onto them. Routes with an identifier we cannot use yet (a capsule, a vote, a wish, an event) fall back to their list.
- Leaving the space signs you out. Core Data cannot keep a `Member` whose space has just been purged from the shared store, so `reloadSession` finds no member and lands on onboarding; signing in again creates a fresh solo space. This is the same shape as joining, which also replaces the local space.
- Deleting the account decides between deleting and leaving from `Space.creatorMemberId` (`SettingsAccountPlan`). A CloudKit failure is reported but does not stop the rest: Apple requires the deletion to finish, so the Apple token is revoked and `StoreReset` wipes the local stores either way.
- `StoreReset` removes each store from the coordinator, destroys it, deletes the sqlite file with its `-wal` and `-shm` sidecars, drops the persistent history tokens and reloads the stores, so the app is usable again without a relaunch.
- Apple revocation needs an authorization code or a refresh token and onboarding stores neither today. `AppEnvironment.storeAppleCredential` takes an optional `authorizationCode` and keeps it in the Keychain under `apple.authorization.code`; deletion revokes only when something is stored. Onboarding has to pass `credential.authorizationCode` for this to fire. Superseded on 2026-09-17: the code is exchanged at sign in and only the refresh token is kept (see the entry of that day).
- Settings is a plain `List` with `SectionCaps` headers rather than the card stack the feature screens use. Twelve sections of one-line rows read better as a list, and the list gives free Dynamic Type row growth and 44pt rows.
- The "See plans" row presents `PaywallView` itself instead of going through `PremiumGate.presentPaywall`. The gate's paywall is presented by `RootView`, and the Us hub closes itself when the gate raises one, which would tear down the settings screen under the user.
- `error.*` and `notification.*` keys were missing from the string catalog even though `CorbieError` and `NotificationScheduler` have been reading them since module 01. They are added here because every toast and every notification in this module renders through them.
- `DebugMenuView` is written in `Corbie/Features/Settings/DebugMenuView.swift` as a DEBUG-only developer screen. The paywall module was asked for the same type name in `Corbie/Features/Paywall`; if both land, delete this one, the settings row calls `DebugMenuView()` either way.
## 2026-09-06 (code quality review)
- Spec section 9 notification 4 ("Event today / tomorrow") is now scheduled: `EventEditorViewModel` schedules the digest next to the offset reminders, `EventDetailViewModel.delete` cancels it, and `NotificationBacklog.resync` reschedules both for every event that has not ended yet. Saving an event asks for notification authorization even without reminder offsets, because every event produces a digest.
- One rule answers "which space is ours". `SpaceRepository.currentSpace(memberId:)` holds the shared-store-first rule that lived in `CloudKitSharing.currentSpace`, and `firstSpace()` is gone, so the widgets, the App Intents, the app and the share extension resolve the same space. `WidgetDataProvider` resolves the viewer from the Keychain apple id before the space, instead of guessing from the members of whichever space came first.
- A Countdown widget configured for an event that is missing renders the empty state instead of the anniversary: `CountdownConfigurationIntent.countdownSource` is optional. `CountdownSnapshot.source` was written and never read, so it is gone.
- One money formatter. `Money.formatted(locale:)` drops the cents of a whole amount, which is what the widgets already did, and `WidgetAmountText` is deleted. It stays skipped for the rest of that cycle and comes back on the next pass through the bank, by which time `togetherSince` has moved. `QuestionBank` reads every JSON file under `Resources/Questions/`, merges them by id and keeps the first file that claims an id; a broken file is skipped rather than fatal, and an empty directory yields an empty bank, which the callers treat as "no question today".
- `dayKey` is `yyyy-MM-dd` in `Space.anchorTimeZone` (falling back to the device zone when it is unset), so two people in two time zones open the same question. `DailyQuestion` has no unique constraint - CloudKit does not allow one - so `CoreDataQuestionRepository.merged` folds duplicates for a day into the oldest record by id and moves the answers over, which is what happens when both devices create the day's record offline.
- Chore split tie rules: both `hate` rotates; a tie where both said `like` is held as shared work and only handed to one person when the balance pass needs it, otherwise it ends as `anyone`; any other tie (both `fine`, both `neutral`) goes to whoever carries less load. Contested items are assigned biggest score gap first and refused when the winner's load would pass `total / 2 + heaviest single item`, which is what stops one daily chore from dragging the whole list.
- The balance pass moves an item only when the move actually shrinks the gap. Moving load L from the heavier side to the lighter one changes the gap by 2L, so the test is `abs(gap - 2 * load) < gap`. The first version compared against a one-sided projection, which accepted moves that made the gap worse and then accepted the move back: a space with one daily and one weekly chore both wanted by the same person span forever. `aSplitThatCannotBalanceStopsInsteadOfSwappingForever` pins it. A split that cannot get within 15 percent now stops instead, which is what the module asks for.
- Ratings are held back in the repository, not in the view. `CoreDataChoreRepository` builds every `ChoreSetDTO` through one renderer that passes `showsEveryRating` only when every included item carries a rating from every member of the space, or the set is already revealed; until then a member sees their own verdicts and nothing of the other's. A CloudKit sync that lands the partner's ratings early therefore changes no DTO.
- Applying a split matches an existing task by the chore's catalog id, or by its lowercased title for a custom one, rather than by `choreItemId` alone: a re-split makes new `ChoreItem` rows, so matching on the row id would duplicate every task on the second run. Chore tasks from the previous set that the new set dropped are archived, not deleted.
- `Recurrence` gained `everyTwoWeeks` and `quarterly` because the chore catalog needs both, and the task editor shows them as two more repeat options. `ChoreFrequency.loadPerWeek` carries the module's weights (daily 7, few times a week 3, weekly 1, every two weeks 0.5, monthly 0.25, quarterly 0.1) and is the only place they are written.
- An open-ended plan stores `targetAmount = 0` and `isOpenEnded = true`; the repository zeroes the target on write so no stale number survives a plan being switched over. `PlanDTO` answers `progress` 0, `leftAmount` 0, `isOverspent` false and `showsProgress` false while open ended, and exposes `total` and `contributionCount` for the card. A withdrawal is an ordinary expense with a negative amount - `PlanExpenseDTO.isWithdrawal` - so the total is the plain sum and no second entity is needed.
- The package publishes its resources as `.process("Resources/Chores.json")` plus `.copy("Resources/Questions")` rather than `.copy("Resources")`. A copied `Resources` directory at the root of a shallow iOS bundle makes `codesign` read the bundle as the old macOS layout and fail with "bundle format unrecognized", which broke the app build; the question files still need a real directory because the bank enumerates it.
- The 44 chore names live in `Chores.json` and the ten group headers live in the string catalog under `chore.group.<group>`, reached through `ChoreGroup.titleKey`. The chore texts are catalog data that grows with the catalog and would put 220 strings into `Localizable.xcstrings`; the group headers are a fixed part of the UI, they are the same ten whatever the catalog holds, and the builder screen needs them without loading the catalog.

## 2026-09-17 (module 21, monetization flag and Apple wiring)

- Monetization is a server value, not a build setting. The requirement is that v1 ships free and a later flip charges everyone, including people who installed during the free period, with no release and no review. A build constant cannot change after install, so it would either grandfather the free installs or need a release to flip, and both are ruled out. The value lives in `public.app_config`, row `monetization_enabled`, and is read by a new public `GET /config`.
- `config` is its own function rather than a field on `entitlement`. The flag is global while `entitlement` is per space and needs a signed-in session; onboarding has to know the flag before a space exists, and the widgets and the share extension read it without a token. Keeping it apart also leaves the `entitlement` contract untouched.
- The client resolves in this order: monetization off beats every other source, including the DEBUG entitlement override, and yields `EntitlementState.monetizationOff`, a premium state with no expiry and no trial clock. Monetization on runs the existing StoreKit, server, CloudKit order unchanged.
- A value that was never fetched counts as off, so a first launch without network opens a free app instead of a locked one. A fetch that fails keeps the last stored value, so a device that has seen `true` never falls back to free on a bad connection. The server answers 500 on a database error for the same reason: a 200 `false` during an outage would unlock the paid app for everyone.
- The value is stored in the App Group defaults under `corbie.monetization.enabled`, so the widgets and the share extension read the same answer as the app.
- While monetization is off nothing is mirrored into the space's CloudKit subscription status. Mirroring the free state as `active` would make the CloudKit-cached source grant premium after the flip, which is exactly the grandfathering the requirement forbids.
- `TrialOfferFlag` is not claimed while monetization is off. Claiming it on the first free launch would mean nobody who installed during the free period ever sees the intro offer after the flip.
- UI tests launch with `-corbie-monetization off` unless they ask for `on`, so a flip on the live server cannot change what the suite sees.
- Universal links, the legal pages and the invite link moved from `corbie.app` to `yourcorbie.app`, the domain that is live and serves the association file. `corbie.app` no longer routes into the app.
- Support is a mail to `support@yourcorbie.app` with a fixed English subject and a body that carries only the device model, system version, app version and build. The address lives in the string catalog, identical in every language, so it changes in one place.
- Every target carries a privacy manifest. The app reads and writes App Group defaults, which is a required reason API (1C8F.1, and CA92.1 for the standard-defaults fallback); App Store Connect refuses an upload that uses one without declaring it. The app manifest declares product interaction (anonymous analytics) and other user content (links pasted for wishes and invite links pass through the server), neither linked nor used for tracking.

## 2026-09-17 (persistence fix round A: who syncs, deleting, leaving)

- Only the app mirrors to CloudKit. The widget extension, App Intents running outside the app and the share extension open the same two App Group files through `PersistenceController.appGroupWithoutMirroring(author:)`: a plain `NSPersistentContainer` with persistent history tracking and remote change notifications on, and no `cloudKitContainerOptions`. Before this, all three processes ran `NSPersistentCloudKitContainer` with mirroring on the same SQLite files. Apple's guidance is one syncing process per store: with three, the same change can be exported or imported by more than one process, and an extension that iOS suspends in the middle of a sync stops in an unknown state. That is the reason for the rule; no duplicate was seen, nothing ran on a device. The price is latency: a widget tick or a shared wish is written at once but reaches iCloud only when the app next runs and its mirroring exports the transactions the extensions left in the store history. That export of another process's writes is the documented behaviour and is not checked on a device yet (`docs/TWO_DEVICE_TEST_SESSION.md` step 8). `IntentPersistence.use(controller:identity:)` still hands the app's own controller to App Intents that run inside the app.
- `CoreDataStack` now says which mode it is in (`StoreMirroring.cloudKit` or `.disabled`). A non-mirroring stack has no `cloudKitContainer`, so `CloudKitSharing` and `initializeCloudKitSchemaIfRequested` refuse it with "CloudKit container is not configured" instead of calling CloudKit.
- Only the mirroring stack deletes history. The extensions keep history, because they cannot know what the app's exporter has already read; a widget process that deleted a week-old tick before the app next ran could delete a change that was never exported. The app deletes history only up to a confirmed upload (see the review entry below).
- The history tokens stay per process (`history.token.app`, `.widgets`, `.share`), each process skips only its own author, and the CloudKit import writes under `NSCloudKitMirroringDelegate.import`, so the app merges and alerts on imports and on extension writes exactly as before.
- Deleting the account removes the user's records on the server first and does not wait for mirroring to export a local delete, because `StoreReset` deletes the store files right after and an export that has not run by then never runs. `CloudKitSharing.purgePrivateZones` calls `purgeObjectsAndRecordsInZone` for the zone of every space in the private store (taken from `recordID(for:)` of the space) and for the default Core Data zone `com.apple.coredata.cloudkit.zone`. Purging a zone deletes it on the server with every record in it, including the `CKShare`, so the partner loses the space too, which is what "The space you own goes with it" says (step 14 of the device session checks it). A zone the server does not know counts as purged.
- A participant who deletes the account first leaves the space the same way the Leave row does (below), then purges their own private zones, so nothing they made before joining stays in iCloud either. Any failure stops the deletion (see the review entry below).
- `CloudKitSharing.deleteSpace` stays for the joiner's own solo space, which `JoinViewModel` drops when joining; account deletion no longer uses it.
- Leaving deletes the participant's own `Member` row in the shared store and frees every task and plan step assigned to them in the same save (`MemberRepository.removeMembersAndFreeTheirTasks`). The row lives in the owner's zone, so without this the owner keeps a partner forever: `partner(of:spaceId:)` returns any second member, the invite rows stay hidden and nobody else can be invited. `leave` first fetches the share from the server, so an offline phone fails before anything is deleted, then saves the removal and waits for a finished export of the shared store that started no earlier than the save (`NSPersistentCloudKitContainer.eventChangedNotification`, `CloudKitExportWait`), up to 20 seconds. A failed or timed-out export is logged and leaving goes on: the owner's cleanup below removes the row anyway.
- The owner cleans up by itself. On launch (`reloadSession`), on foreground (at most every 5 s) and after merged remote changes (at most every 60 s), `AppEnvironment.reconcilePartnerMembership` first checks that the session's partner is still in the store and reloads the session if the row is gone, which is how an exported leave shows up. Then, on the owner's phone only, `CloudKitSharing.removeDepartedMembers` fetches the current share from the server and hands the participants to `DepartedMemberRule`: when no participant other than the owner is accepted, pending or unknown, every member of the space except the owner is removed with their tasks freed, and the session is reloaded so Settings shows the invite rows again. An accepted, pending or unknown participant, no share, no network or any CloudKit error means nothing is removed; errors are logged, never shown.
- The share is read from the server, not from `fetchShares(matching:)` alone. The local copy is what this phone last imported, and with a public share the joiner is not a participant until they accept, so a stale local copy that still lists only the owner next to a freshly imported joiner row would delete a real partner. The member ids are read before the server fetch, so a row that arrives after it is never in the removal list.
- The partner check is paused while leaving or deleting the account runs (`AppEnvironment.withPartnerChecksPaused`, a counter, so two overlapping runs do not unpause each other). Purging a zone deletes local rows, the merge of that deletion would start a check, and a check in the middle would reload the session and sign out before the wipe had finished.
- A partner who deletes the app without leaving is still an accepted participant, so the owner keeps them. The share does not say whether a participant still has the app, and the rule does not guess.
- The Leave row is shown only to the participant, by the same creator rule that `SettingsAccountPlan.decide` uses for deletion (`SettingsAccountPlan.offersLeaving`). The owner could only ever get a toast from it.

## 2026-09-17 (fix round B: partner changes while the app is not on screen)

- The app delegate owns `AppEnvironment` and `AppState` and creates them on first use, which is `didFinishLaunching` or the first `CorbieApp.body`, whichever comes first; the window reads both from the delegate. The delegate is the one object iOS creates on every launch, including a background launch for a silent push where no scene connects. Before, the environment lived in the `App` struct and reached the delegate only from the window's `.task`, so a push-launched process had no alert audience and no widget reloader. A process-wide static would also work, but it hides who owns the environment and adds a second global next to `PersistenceController.shared`. The debug launch arguments run inside that lazy creation, right before the store opens, because the order of `App.init` and the delegate's init is not documented.
- `AppEnvironment.startProcess()` runs from `didFinishLaunching` and runs once: it points `IntentPersistence` at the app's controller, starts `WidgetReloader`, then in a task registers the notification categories, loads the session with its alert audience and starts `RemoteChangeNotifier`. `processReady()` awaits that task. The window's `bootstrap`, the push handler and the notification actions all await it, so nothing is started twice.
- Loading the session is split from what only an opened app does. `loadSession` reads the member, space and partner, sets the audience, resyncs the notification backlog and applies the cached entitlement. `runSessionUpkeep` writes `lastSeenAt`, refreshes the entitlement, publishes busy times and runs the partner check; `reloadSession` does both. A background launch only loads, and the window runs the upkeep when it appears. Without the split, every push-launched process would write `lastSeenAt`, that write reaches the other phone as a push, and two phones could keep waking each other. A process that started in the background and found no signed-in member loads the session again when the window appears, in case the keychain was unreadable at that moment.
- The history observer of the mirroring stack keeps the change records it merges while no handler is installed and hands them over when `RemoteChangeNotifier.start()` installs one, and the notifier now starts after the session and its audience are loaded. Before, the observer started with the stack and dropped the records of any import that finished before the window's bootstrap. The extensions' stacks do not keep records, because nothing reads them there.
- The push handler (`RemotePushSync`) waits, within 25 of the 30 seconds iOS allows: up to 20 seconds for an import of the pushed database (`CKDatabaseNotification.databaseScope`) that was running when the push arrived or started after it, then for a history pass, then for every classification the notifier has started (`RemoteChangeNotifier.waitForPendingChanges`, `InFlightTasks`). It answers `newData` when a merge happened meanwhile, `failed` when the import failed and nothing merged, `noData` otherwise, and `Deadline.run` answers with what is known so far when the 25 seconds run out. `CloudKitRunningImports` tracks imports that started and have not ended, for the case where the container begins its launch import before the delegate hears about the push. Which of the two comes first on a device is not known. A wait that never matches costs 20 seconds of background time and loses nothing, because the observer classifies an import whenever it lands. Each push logs the store, the import outcome, the answer and the seconds it took (subsystem `app.corbie`, category `remote-push`) for the device session to read.
- `CloudKitExportWait` is now `CloudKitSyncWait` and takes the event kind, so the export wait for leaving and the import wait for a push are one class. An import wait without a store accepts any store.
- The Take and Done notification actions no longer wait for a window: they run after `processReady()`, and the delegate calls the completion handler once the write has finished. Before, Done tapped on a locked phone was queued until Corbie was next opened.
- The session's partner follows the store. `AppEnvironment.reloadSessionIfPartnerChanged` reloads the session whenever the stored partner differs from the session's partner in a field the app shows: who it is, name, colour, birthday, joined date or the busy times switch (`PartnerChangeRule`). The partner's own bookkeeping (`lastSeenAt`, recap and Us visits, the question day seen, notification preferences) is ignored, because `reloadSession` writes `lastSeenAt` and each phone's reload would otherwise trigger the other's. ## 2026-09-17 (less personal data on the server, quiet debug builds)

- Why: on a two-phone session the anniversary reverted after it synced. ## 2026-09-22 (a sync log for device sessions, and one question of the day per day)

- Why the log: on a two-phone session several entities did not reach the other phone, and the code review found every create path puts the object in its parent's store with the parent set. Without device logs there is no way to tell whether a record was never exported, went to the wrong zone, or was never imported. The next session should answer that from Console alone.
- `CloudKitActivityLog` (CorbieCore, `Persistence/CloudKitActivityLog.swift`) is started by `CoreDataStack` only when mirroring is CloudKit, so the widget and share extensions do not run it. It listens to `NSPersistentCloudKitContainer.eventChangedNotification` and writes to subsystem `app.corbie`, category `sync`. On each finished export or import it reads that store's persistent history after its own mark for that store and direction (App Group defaults `sync.log.token.<export|import>.<private|shared>`, separate from the history observer's token), keeps our model entities, asks `recordIDs(for:)` for each changed object's zone, and writes one line per zone and entity with insert, update and delete counts. An export counts transactions not written by the mirroring delegate (author not starting with `NSCloudKitMirroringDelegate.`) and saved before the export started, so a change saved during an export shows under the next one. An import counts transactions written by `NSCloudKitMirroringDelegate.import`. A delete whose record id is gone is logged under `zone=unknown`. An update that only touches to-many relationships is left out: adding a wish also marks the space as changed in the history, but the reference travels on the wish record.
- Marks: a missing mark is set to the current end of history when the log starts, so the first launch of this build does not replay a week of history. A failed event does not move the mark, so its changes are logged by the next successful one. History cleanup (`HistoryCleanupRule`: older than seven days and older than the last upload) can delete what a mark points to after a long pause; Core Data then answers "token expired", the log writes `history restarted` and carries on from the current end. `StoreReset.clearHistoryTokens` clears the marks with the other tokens.
- Line formats, fixed so they can be grepped: `export ok store=private zone=<zone> Wish +2 ~1 -0`, `import ok store=shared zone=<zone> Wish +1 ~0 -0`, `export ok store=private no model changes`, `export failed store=private domain=CKErrorDomain code=2` (with ` underlying=<domain>/<code>` when the error wraps one), then per record `export failed store=private record=<recordName> zone=<zone> code=14` for at most 20 records and `export failed store=private dropped <n> more record errors`, `setup ok store=private`, `setup failed store=...`, `zones store=private spaces=<zones> shares=<zones>` once per store per launch after its setup (from `fetchShares(in:)` and the record ids of the stored spaces, both local metadata, no network), `export history restarted store=private reason=expired`, `purge asked store=shared zone=<zone> reason=leave|deleteAccount` followed by `purge ok|missing|failed ...` from `CloudKitSharing`, and `question consolidation merged <n> rows over <d> days`. Failures are error level, everything else notice. Lines hold entity, zone, record and store names and counts only, never titles or text, and are logged public.
- Why the question of the day needed more than the log: each phone creates its own `DailyQuestion` row for a day before it sees the partner's (CloudKit allows no unique constraint). `todaysQuestion` folded the rows, but `storedQuestion`, the history and everything built on them read the lowest-id row alone, so an answer written on the other row was invisible until this phone's next `todaysQuestion`.
- Reads now see the day, not a row. `QuestionDayMerge` builds a day from every row with that day key: the lowest id is the canonical row, answers come from all rows with one per member, and the latest nudge wins. `storedQuestion`, `history`, `todaysQuestion`, `answer`, `editAnswer` and `nudge` all return that view; a read writes nothing. `answer` and `nudge` write to the canonical row, and "already answered" looks at every row of the day.
- One answer per member: the answer written last (`createdAt`, then the higher id) stays and the others are deleted. The old merge kept the canonical row's answer. With one phone per member that is the same answer, because a phone answers on the lowest row it knows, so a second answer always sits on a lower row than the first. The rule had to stop depending on the row: two phones that know different rows would otherwise each delete a different copy and lose both.
- `consolidateDuplicates(spaceId:now:)` applies the same merge to every day of the space: answers move to the canonical row, extra answers of a member are deleted, the latest nudge is copied, and duplicate rows are deleted once their day is before yesterday in the anchor time zone. Only rows that change are written. A read decides first whether anything needs a write, so the usual run is one fetch and no save. `todaysQuestion` uses the same function.
- Why duplicate rows of today and yesterday stay, empty, until the day is over: `DailyQuestion.answers` cascades. If phone A deletes phone B's row while B's person is still answering on it (B has not seen A's row yet), B's answer reaches both phones pointing at a deleted row and is gone. Answers are only written for today, so a row a day past its day gets nothing new. Before this change `todaysQuestion` deleted today's duplicate at once.
- Why it runs at every session upkeep and not once: the founder asked for a one-time cleanup of existing duplicates, but the partner's row for a day can arrive after this phone's last write of that day, so a one-time pass would leave every later duplicate in place. The run is idempotent and cheap as above. It is called from `AppEnvironment.runSessionUpkeep` (launch and session reload) and on every return to the foreground (`RootView`).
- Two phones consolidating at once pick the same canonical row and the same winning answer from the same rows, so they write the same thing. Phones that know different rows converge once both have all rows, at the next upkeep.

## 2026-09-22 (a price without a currency takes its currency from the link)

- Why: the server often returns a price with `currency: null`, and the wish editor, the share extension, the background retry and the gift idea editor then labelled it with the picker's currency. The founder: a wrong price is worse than an empty field, because people trust a filled one.
- `LinkParser` decides this once for all four. A currency returned by the parse always wins: a supported one keeps its price, an unsupported one drops the price as before, and the link never replaces either. Only a price with no currency goes to `LinkCurrencyInference`, which reads the link the server landed on (`canonicalURL`, so `amzn.eu/d/...` counts as the `amazon.de` page it resolved to). A supported result keeps the price with that currency. Anything else drops the price and the currency and keeps the title and the photo. There is no network call and no server change.
- Order: the path first, then the host. The first path segment is read, and the second only when the first is a bare language (`/en/gb/`). A segment names a country when it is a language-country pair (`en-gb`, `de_DE`, `fr-CH`) or a bare country code (`/us/`, `/gb/`, `/uk/`). A pair is read as country first (`ch-de`, `gb-en`) only when its first half is not a language. The host is read from its last label, so `.co.uk`, `.com.au`, `.co.nz` and `.co.jp` need no separate list.
- A bare code that is also a language (`de`, `fr`, `it`, `es`, `nl`, `ca`, `be`, `uk`, `cy` and others) counts as a country only when the host names no country. Swiss and Canadian shops put the language in the path (`galaxus.ch/de/...`, `canadiantire.ca/fr/...`). Reading that segment as a country would give EUR, but the host says CHF or CAD. On `.com`, `/de/` is Germany and `/ca/` is Canada. A bare language with no country (`/en/`, `/ja/`) tells us nothing.
- A country outside the table gives no currency and ends the search. `en-in` on a `.co.uk` host means India, not the UK, so the price is dropped. For the rule above, any two-letter last label counts as naming a country, including `.eu`, `.io` and `.co`, so a bare `/de/` on those hosts gives nothing. The table maps only to the eight: `us` USD; `gb` and `uk` GBP; `ca` CAD; `au` AUD; `nz` NZD; `jp` JPY; `ch` and `li` CHF; the 21 euro countries EUR, including Bulgaria (euro since 2026-01-01). `.com`, `.net`, `.shop` and other generic hosts name no country.
- Known miss: Samsung writes the country first even when that code is also a language (`samsung.com/ca_fr/`), so that segment reads as French in France and gives EUR. BCP 47 puts the language first and `fr-ca` is much more common, so the rule follows BCP 47.
- Log (category `wishes`, notice): `link price kept host=... canonical=... currency=none inferred=GBP from=path|host` and `link price left out host=... canonical=... currency=none inferred=none`. The unsupported-currency line is unchanged. This replaces the last sentence of the link parse item under "dollars by default, eight currencies, no rubles".

## 2026-09-23 (store loading is one at a time in a process)

- The full core run crashed once with `EXC_BAD_ACCESS` inside Core Data (`NSSQLEntity_DerivedAttributesExtension _generateTriggerSQL`, a nil key into a mutable dictionary) while five tests were creating SQLite stores at the same moment. Every stack is built from the one `CorbieModel.shared`, and Core Data fills parts of the model's SQL description lazily the first time a store creates its tables; two stores doing that at once race. The app, the widgets and the share extension each open their stores once, one after the other, so a device should not hit it; the test process, which runs suites in parallel and builds hundreds of stacks, does.
- `CoreDataStack.load` now takes a process-wide lock (`oneStoreLoadAtATime`) around `loadPersistentStores`. Loading is rare and short, so the lock costs nothing on a phone, and it also covers `reloadStores` after a reset. The alternative, a model per stack, would let two stacks disagree about entity identity in the same process, and serializing test suites would leave the same trap for any future code that opens a second stack.

The task named `original_transaction_id` alone as the key; the environment is part of it so that "a sandbox notification never changes a production row" is a property of the key and not of Apple's id ranges, which I did not find documented as disjoint. ## 2026-09-25 (an App Review purchase always unlocks, a sandbox purchase never reaches a customer)

- The question: App Review runs the production-signed build, but its purchases happen in the sandbox and Apple sends their notifications to the sandbox URL. Apple does not document what `AppTransaction.environment` reports under review; its receipt guidance only says to handle a production build whose purchases come from the test environment "while your app is in testing, in review by App Review, or live in the App Store". So the code must work whether the review build reports production, sandbox, or no app transaction at all.
- What was wrong after the paid-v1 batch: the client dropped every local transaction whose environment differed from the build's, the server answered 400 to a sync whose transaction environment differed from the build's proof, and the widgets and the notification and widget actions read only the iCloud mirror, which sandbox builds no longer write. A reviewer on a build reporting production (or none) would have bought, and stayed locked; on a build reporting sandbox, the app unlocked but the widgets and the Done and Take actions did not.
- How the two are told apart now: by the environment Apple signs into each transaction, not by the build. StoreKit only hands a build the transactions of the environment it runs in, so a customer's App Store install never holds a sandbox transaction; only Xcode, TestFlight and review builds do. Therefore the device's own transactions count whatever their environment (the reviewer unlocks), and a sandbox transaction is kept on that device: the iCloud mirror is written from production transactions and production server rows only, the server stores a synced transaction under its own signed environment and answers each caller from the environment its verified `AppTransaction` proves (no proof or an unverifiable one reads Production), and the widgets and intents trust `DeviceEntitlementStore`, this device's own last resolution, only when its environment equals the widget's own `AppTransaction` environment.
- The one gap left: a tester whose TestFlight build could not load its `AppTransaction` stamps its device snapshot as production; if that phone then installs the App Store build and never opens it, its widgets follow the snapshot until the sandbox expiry. It is the tester's own phone, it never reaches another person or the server, and the first launch overwrites it.
- Tests: `aReviewersSandboxPurchaseUnlocksWhateverEnvironmentTheReviewBuildReports` (production, sandbox and missing proof; the app, the mirror, the widgets and a relaunch), `aSandboxPurchaseNeverReachesARealAppStoreCustomer` (the partner on the App Store, the same phone switched to the App Store build, the widgets), `theWidgetsAndIntentsFollowThisDevicesOwnPurchaseOnlyInTheSameEnvironment`, and on the server "a reviewer's sandbox purchase from a production-signed build is kept in Sandbox and never answers Production".
